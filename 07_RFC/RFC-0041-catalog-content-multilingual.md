# RFC-0041 — Мультиязычность данных каталога и контента салонов (el / en / ru / uk)

Статус: **DRAFT (дизайн, без кода)**, 01.11.2026. Автор: интегратор, по заданию архитектора. Номер 0041 — следующий свободный после 0040 (RFC-0040 «Заказы поставщикам» — ветка `docs/rfc-0040-supplier-orders` на origin, отдельный docs-PR).

Written against main 3fbb8abd; §1 'what exists' to be re-verified before approval.

Что это не есть: не реализация, не юридическое заключение, не решение «делаем / не делаем». Ничего не включает; миграций и их номеров не берёт (0104–0109 зарезервированы цепочкой, RFC-0034 идёт после 0109; номер миграции этого RFC — «следующая свободная», назначает архитектор). Флаг — только тёмный, включение — решение пользователя. Платный провайдер перевода и платный массовый прогон — только по личной фразе пользователя.

**Допущения помечены «Допущение».** Прод-БД не читалась: сколько салонов имеют описание, сколько переводов уже накоплено, сколько стоит текущий расход — неизвестно. Всё про «что есть» — из кода main `3fbb8abd`.

## 1. Что уже есть и чего нет (проверено по коду main 3fbb8abd)

### 1.1. Данные: где живут языковые версии

| Сущность | Колонки (backend/app/models) | Особенности |
|---|---|---|
| Салон, описание | `salons.description` (**en**, без суффикса), `description_el`, `description_ru`, `description_uk` (`salon.py:18–21`) | Английский лежит в колонке БЕЗ суффикса; название салона (`name`, `name_el`) не переводится. |
| Услуга, название | `services.name` (исходное, NOT NULL), `name_el`, `name_en`, `name_ru`, `name_uk` (`salon.py:200–206`) | `services.description` — одна колонка, без языков. |
| Мастер, bio | `professionals.bio` (**en**), `bio_el`, `bio_ru`, `bio_uk` (`professional.py:29–32`) | Тот же перекос: английский без суффикса. |
| Отзыв, текст | `reviews.text` (оригинал), `text_en`, `text_ru`, `text_uk` (`salon.py:255…`) | Колонки `text_el` нет: оригинал считается греческим (допущение кода: `translate_batch` пишет «from Greek or English»). Собственные отзывы Lookla (`source='lookla'`) не переводятся вовсе (`/own-reviews`). |
| Категории услуг | в БД только `name_en`, `name_el` (`ServiceCategory`); ru/uk — словарь `meta` в `routers/categories.py` (`LANG_FIELD` для ru/uk отдаёт `name_en`) | Часть языков живёт в коде, а не в БД. |

Для каждой пары «исходный язык» нигде не хранится: поле `source_locale` приходит только в запросе кнопки перевода (`TranslateDescriptionIn.source_locale`, значение — язык кабинета владельца, решение T-166). Какой текст оригинал, а какой перевод, в БД не записано, ни для описаний, ни для названий услуг.

### 1.2. Перевод: три разных механизма

1. **`app/services/translate.py` → `translate_batch(texts, target_lang, point=, salon_id=)`** — единственная точка вызова провайдера. Провайдер — OpenAI chat (`gpt-4o-mini`, `temperature=0.1`, `max_tokens=4096`), ключ `OPENAI_API_KEY` из окружения. Идёт через `prompt_guard` (`registry.get(point)`, `guard.prepare` с маскированием ПДн, `limits.spend`, `guard_client.chat_completion`, `journal`). Цена за миллион токенов в настройках: `prompt_guard_translate_price_in_eur_per_m=0.14`, `…out…=0.55`. Исключение `TranslationSkipped` — гард не пустил вызов (рубильник, суточный потолок, недоступен счётчик): вызывающий НЕ должен сохранять непереведённый текст как перевод. При любой другой ошибке функция возвращает исходные тексты (ловушка: «перевод» неотличим от провала — владельческие ручки сравнивают результат с источником).
2. **Ленивый перевод при чтении (публичный)**: `GET /api/salons/{id}/services?lang=` и `GET /api/salons/{id}/reviews?lang=` (`routers/salons.py:1212, 1275`). Для настоящего пользователя недостающие `name_<lang>` / `text_<lang>` переводятся на лету и **сохраняются в БД**, ответ несёт `is_translated` и `name_original`. Для ботов (`is_bot(user_agent)`: пустой/короткий UA или список ботов) отдаётся `[]`. Точки реестра: `translate.service_name` (2000 знаков), `translate.review_text` (4000), общий платформенный суточный потолок на обе — `prompt_guard_public_translate_daily_limit=2000` (`limits.PUBLIC_TRANSLATE`).
3. **Кнопки владельца/мастера** (T-166): `POST /api/owner/salons/{id}/translate-description` (`owner.py:1855`, право `salon.edit`, 20/час) и `POST /api/masters/me/translate-bio` (`masters.py:~160`, 20/час). Переводят на три остальных языка и **ничего не сохраняют**: возвращают `{translations, failed_locales}`, владелец смотрит/правит и сохраняет обычным `PUT /salons/{id}`. Точки реестра `translate.salon_description`, `translate.master_bio` (8000 знаков).

`app/services/moderation.py` — **не про переводы**: `is_disposable_email`, `check_text` (OpenAI Moderation) и `check_image` (Google Vision SafeSearch). `check_text` и `check_image` **спят**: их никто не вызывает (регистр `moderation.text` / `moderation.image`; гейт падает, если у них появится вызывающий до LIA 4.5 и публичного раскрытия). Переведённый и введённый владельцем текст сегодня **не модерируется**.

### 1.3. Фронтенд: UI-i18n и данные — две разные вещи

- **UI-строки**: `next-intl`, `frontend/messages/{el,en,ru,uk}.json`, маршрутизация `frontend/i18n/routing.ts`; `el` — по умолчанию, без префикса, остальные — `/en`, `/ru`, `/uk`. Эта часть к данным каталога отношения не имеет и в RFC не меняется.
- **Данные салона** на странице салона: `frontend/lib/salonSeo.ts → salonDescriptionFor(salon, locale)`: `el: description_el || description`, `ru: description_ru || description`, `uk: …`, `en: description`. То есть **запасной вариант — колонка `description` («en»), в которой на деле может лежать греческий текст**: русскоязычный посетитель без `description_ru` получит то, что лежит в `description`, без пометки. Пометка «переведено» на странице салона вычисляется эвристикой (`SalonDetailClient.tsx:391`: описание ≠ `description_el || description` и язык ≠ el), а не данными.
- **Бейдж `TranslatedBadge`** показывается у услуг и отзывов по `is_translated` (`SalonDetailClient.tsx:264, 705`; типы `ServiceItem`, `ReviewItem` в `lib/api.ts`). «Показать оригинал» есть у услуг (`name_original`), у отзывов — нет (`reviews.test.ts` прямо проверяет, что «Show original/Translated from» не придуманы).
- **SEO**: `lib/seoAlternates.ts → buildAlternates(locale, path)` — canonical на URL ТЕКУЩЕЙ локали (перевод — отдельная страница, не дубль греческой), `languages` = hreflang для всех четырёх локалей + `x-default` (на `el`). `lib/sitemapEntries.ts` — для каждой локали статические страницы и страницы салонов с теми же alternates; `app/sitemap.ts`. `<meta description>` салона — `salonMetaDescription(salon, locale)` (160 знаков, по тому же `salonDescriptionFor`).

### 1.4. Чего нет

- Метаданных перевода: кто автор (машина / человек), с какого языка, от какой версии источника, когда.
- Инвалидации: правка исходного описания не трогает переводы (они остаются в колонках и устаревают). Для услуг есть единственный случай: переименование сбрасывает `name_el/en/ru/uk` — и **только при включённом `FEATURE_SERVICE_TEMPLATES`** (`owner.py:1967–1986`); при выключенном флаге старые переводы переименованной услуги остаются.
- Различия «владелец вручную ввёл `name_ru`» и «машина»: оба — просто колонка; ленивый перевод пишет только в пустую, но после этого ручную правку от машинной не отличить.
- Переводов для `services.description`, названия салона, адреса, категорий в БД (ru/uk), `own-reviews`.
- Содержимое для краулеров: ботам `/services` и `/reviews` отдают `[]`, поэтому переведённые названия услуг и отзывы **в SEO-выдаче видны только если их отдаёт серверный рендер из другого источника** (Допущение: страница салона рендерится на сервере из `GET /salons/{slug}`; кусочки `/services`, `/reviews` грузятся клиентом и ботами не видны. Не проверено по HTML живой страницы).
- hreflang объявляет все четыре версии **всегда**, даже если на `/ru/salons/x` текста на русском нет (запасной вариант — чужой язык). Это тонкие дубли в индексе.

## 2. Дизайн

### 2.1. Принцип

Один оригинал (язык, на котором автор написал текст), любое число производных переводов; про каждый перевод известно, **машинный он или человеческий** и **от какой версии оригинала**. Пользователю машинный перевод всегда показывается с пометкой «перевод» (и ссылкой «оригинал»); человеческий — без пометки. Перевод никогда не выдаётся за оригинал, оригинал — всегда доступен.

### 2.2. Хранение: колонки или таблица

**Вариант А — оставить колонки, добавить метаданные.** Для каждой группы колонок завести `<field>_source_locale`, `<field>_origin` (jsonb: по языкам `machine|human`), `<field>_src_hash`. Плюс: ноль изменений в чтении. Минус: колонки `description` («en») / `bio` уже перекошены; на каждое новое поле — 3–4 служебные колонки; новый язык = миграция на все таблицы.

**Вариант Б (рекомендую; **принят — решение архитектора 01.11**: отдельная таблица `content_translations`) — таблица `content_translations`.**
`(entity_type, entity_id, field, locale)` — уникальный ключ; `text`; `origin` (`source` / `machine` / `human`); `source_hash` (хэш исходного текста, от которого сделан перевод); `status` (`fresh` / `stale`); `created_at`, `updated_at`, `edited_by`; для машинных — `model` и `request_ref` из журнала `prompt_guard`. `entity_type` — закрытый список (`salon.description`, `service.name`, `service.description`, `staff.bio`, `review.text`). Оригинал остаётся в исходной колонке (`salons.description*`, `services.name`, …) — **колонки не удаляем и не переименовываем**, на переходе пишем в оба места (двойная запись), читаем сначала из таблицы, потом из колонки. Плюс: новый язык — строка, а не миграция; метаданные на каждую строку; чистая инвалидация. Минус: джойн/подзапрос на публичных ответах (кэшировать на уровне ответа; Допущение: список услуг салона — до ~50 строк, один дополнительный запрос на страницу).

Колонку «исходный язык» хранить явно: `source_locale` на оригинале (в той же таблице — строка с `origin='source'`), а не выводить из языка кабинета (сегодня так — и это уже ломается, когда владелец пишет по-русски при кабинете на греческом).

### 2.3. Цепочка подстановки при чтении

Для запрошенной локали L, поле F:
1. перевод L с `origin=human` (любой `status`) → показать без пометки;
2. перевод L с `origin=machine`, `status=fresh` → показать с пометкой «перевод» + «оригинал»;
3. оригинал (на его языке) с пометкой «оригинал: <язык>»; **не** подмена «английской» колонкой;
4. пусто.

Устаревший (`stale`) машинный перевод не показывается (п. 2 требует `fresh`) и ставится в очередь на пересоздание. Устаревший человеческий показывается, но в кабинете владельца помечен «оригинал изменён после этого перевода».

### 2.4. Инвалидация

Правка оригинала (любой путь записи: `PUT /salons/{id}`, `update_service`, bio мастера, импорт) считает новый `source_hash`; все производные строки с другим хэшем становятся `stale`. Одно место: сервис `content_i18n.set_source(entity, field, text, locale)`, через который идут все записи (тест-страж ловит прямую запись в оригинальные колонки). Это закрывает дыру 1.4 (переименование только под флагом шаблонов).

### 2.5. Когда переводить

Сегодня перевод услуг/отзывов запускается **посетителем** (публичный GET) и считается из общего потолка 2000/сутки; боты получают пусто. Предлагаю перенести перевод **на запись**: сохранение оригинала владельцем → фоновая задача (Допущение: используем уже существующий шаблон cron/CLI-задач вроде `booking_requests/cli.py`; отдельной очереди не заводим) делает машинные переводы на недостающие языки. Результат: страница для краулера и посетителя одинакова, публичный GET больше не тратит деньги (убирается вектор «обход сайта с разных UA съедает потолок»). Для отзывов Google (оригинал приходит краулером, а не владельцем) перевод по-прежнему лениво при первом показе реальному пользователю, но через ту же таблицу и с тем же потолком; ботам — не переводим (как сейчас).

Кнопка владельца «Перевести на другие языки» остаётся как предпросмотр: результат попадает в `origin=human` только после сохранения владельцем (как сегодня). Автоперевод на записи — это `origin=machine`. **Решение архитектора 01.11: автоперевод по умолчанию — ленивый** (на первом показе реальному пользователю, не на записи и не для ботов) **с видимой меткой «перевод»**; перевод на записи (описанный выше) включается отдельным решением, не по умолчанию. Включение по салону/для всех — вопрос 7.3 (остаётся за пользователем).

### 2.6. Модерация

`moderation.check_text` спит и должен остаться спящим до LIA 4.5 и публичного раскрытия (гейт). Предлагаю две ступени, без нового провайдера: (1) всё, что уходит в `translate_batch`, уже идёт через `prompt_guard` (маскирование ПДн, лимиты, журнал); (2) вывод машины проверяется тем же `guard` (`restore` плейсхолдеров, длина, совпадение числа элементов) и отклоняется, если перевод слишком короткий/длинный относительно оригинала или содержит символы чужого алфавита (простые проверки, без вызова). Включение `moderation.check_text` для переведённого текста — отдельное решение после LIA 4.5, не часть этого RFC.

### 2.7. SEO

- hreflang и строки sitemap выдаются **только для локалей, где у страницы есть содержимое** (оригинал или `fresh`/`human` перевод описания); для остальных — не объявлять и не ставить в sitemap, а страницу самой локали отдавать с `noindex` и canonical на локаль оригинала, пока перевода нет. Цель: убрать тонкие дубли.
- `x-default` — страница на языке оригинала, а не безусловно `el`.
- **Решение архитектора 01.11:** машинный перевод без человеческой правки — `noindex` и **вне hreflang и sitemap** до проверки (правка владельцем или иная проверка переводит его в `origin=human`); пометка «перевод» остаётся на странице. Это снимает риск оценки автогенерированного контента (вопрос 7.5 решён).
- Серверный рендер страницы салона должен получать переводы списка услуг вместе с карточкой салона (чтобы они были в HTML), а не только клиентским `fetch` (проверить по 1.4).

### 2.8. API

Публичные ответы получают, где уже есть `is_translated`, дополнительно `translation: {origin, source_locale}` (обратно совместимо: `is_translated` остаётся). `lang` остаётся тем же параметром. Владельческие чтение/запись: `GET/PUT /api/owner/salons/{id}/content` отдаёт все четыре языка с `origin`/`status`; существующие поля `description_*` продолжают работать на двойной записи (серверное ужесточение — после того, как клиенты перейдут, не раньше).

## 3. Права

- Оригинал и переводы салона, услуг: `salon.edit` / `services.edit` (существующие ключи); менеджер — как сегодня; бухгалтер и прочие — нет.
- Био мастера: сам мастер (`professionals.user_id`), как сегодня.
- Админ платформы: правка и пересоздание перевода по любому салону с записью в журнал админ-действий (Допущение: журнал админ-действий существует — уточнить имя при реализации).
- Кнопка перевода: 20/час на пользователя (как сейчас) + общий суточный потолок `prompt_guard`.
- Посетитель: только чтение; публичный GET не запускает перевод описаний/названий услуг (после Ф3).
- Новые права не заводятся; роли и их права этим RFC не меняются.

## 4. Фазы, тесты

Всё за тёмным флагом `FEATURE_CATALOG_I18N` (название предварительное).

- **Ф0.** Решения раздела 7, ответ юриста по разделу 6. Кода нет.
- **Ф1.** Миграция: таблица `content_translations`; сервис `content_i18n` (чтение с цепочкой 2.3, запись `set_source` с инвалидацией); двойная запись из существующих ручек; флаг выключен — поведение прежнее. Бэкфилл существующих колонок в таблицу — скрипт без внешних вызовов (оригиналы и существующие переводы как `origin=unknown→human`; Допущение: все накопленные `name_en/ru/uk`, `text_en/ru/uk` — машинные, так как только машина их писала; описания — человеческие).
- **Ф2.** Чтение через таблицу под флагом; пометки «перевод»/«оригинал»; hreflang/sitemap/noindex по 2.7; фронт (w1).
- **Ф3.** Перевод на записи (2.5), отключение ленивого перевода в публичном GET для услуг; стоимостной учёт в журнале `prompt_guard`.
- **Ф4.** Платный бэкфилл машинными переводами недостающих языков — **массовый платный прогон, только по личной фразе пользователя** (подтверждено 01.11); оценка в разделе 5.
- **Ф5.** Снятие колонок `name_en/…`, `text_en/…` — отдельный RFC после наблюдения.

Тесты (минимум):
1. Цепочка 2.3: human > fresh machine > оригинал; stale machine не показывается; «английская» колонка не подставляется вместо оригинала.
2. Правка оригинала (каждый путь записи) → производные `stale`; прямая запись в оригинальную колонку мимо сервиса ловится стражем.
3. Двойная запись: старые клиенты (колонки `description_ru`) и новые (таблица) видят одно и то же.
4. Публичный GET не вызывает `translate_batch` для описаний/названий услуг (после Ф3); бот по-прежнему не вызывает вообще.
5. `TranslationSkipped` и «провал = эхо источника» не сохраняются как перевод (регрессия на оба сегодняшних сценария).
6. hreflang/sitemap: локаль без содержимого не объявляется, страница получает `noindex`; `x-default` = язык оригинала.
7. Пометка «перевод» присутствует у машинных и отсутствует у human; «оригинал» отдаёт исходный текст.
8. Отказ рубильника/суточного потолка: страница отдаётся с оригиналом, без 5xx.
9. Маскирование ПДн в тексте описания (телефон, e-mail) до отправки провайдеру (существующий тест-набор `prompt_guard` + новый кейс на описание).
10. Привилегии: менеджер правит, бухгалтер — 403; чужой салон — 404/403 по матрице изоляции.

## 5. Стоимость и риски

- **Оценка стоимости (Допущение, токены на глаз):** описание ≈ 150–500 слов ≈ до 700 токенов; на три языка — вход ≈ 2 100, выход ≈ 2 100 токенов. По ценам из настроек (0,14 / 0,55 €/млн) — **≈ 0,0015 € на салон**; для верхнего предела 8000 знаков (~2 000 токенов) — ≈ 0,005 €. Даже для всех 6 950 салонов бэкфилл — порядка **10–35 €** верхняя оценка, реально меньше (не у всех есть описание). Нужен реальный подсчёт `SELECT count(*) …` по описаниям — я прод не читаю; прошу архитектора/пользователя дать число, либо посчитаю на скрейп-копии, если такая появится.
- Риск: машинный перевод с ошибкой в названии услуги/цене — мало; в описании — репутационный (владелец отвечает за текст?) → вопросы раздела 6.
- Риск: ленивый перевод отзывов привязан к посетителю и общему потолку; при исчерпании потолка отзывы остаются на оригинале (ожидаемо).
- Риск: двойная запись расходится при ошибке — страж 4.2 и ночной сверочный отчёт «колонки vs таблица».
- Риск SEO: оценка автогенерированного контента (вопрос 7.5).
